# GPT 需求发现定时任务 SOP 草案（待用户审核，未启用）

版本 v0.3 / 2026-11-13（Issue #1 第二轮复审修订）。此文件是供未来 GPT 自动任务读取的执行规格，**并未创建任何定时任务**。

## 目标
发现适合单人低成本运营、英语 SEO 可获客的精品工具页、Micro SaaS、AI 图片/视频细分工具及 H5 游戏相关需求。优先开发验证时间在 7 天内、总计约 8–12 工时以内、可复用 Next.js/React/Tailwind/Cloudflare 或 Vercel 的机会。先需求验证，不直接开发。

## 启动前的强制阅读
1. 读取仓库 `https://github.com/owenlee669/reqs-geifei` 的 main 分支 `docs/methods.md` 和本文件的**最新版本**。
2. 读取 `data/opportunities.jsonl` 的去重键和必要候选状态/历史变化；**包括周日也不加载 `reports/` 全部历史全文**。候选池较大时按索引/分段读取并注明覆盖范围；文件不存在视为首次运行。周日仅总结候选池的 `first_seen`、`last_seen`、`status_history` 和 `score_history` 本周变化，报告注明「基于候选池状态变化，非逐日运行报告回顾」。
3. 文中原始分享是**方法**，不能当作当天新发现、也不能拿旧数据直接作为当前机会。
4. 若 GitHub 无法读取、某网站 403、无付费 API，记录不可用；改用公开可访问的合规数据，不准虚构查到的结果。

## 8 步执行：发现阶段允许证据缺失

1. 保存具体原始网页、帖子、评论或 Issue 直链、原始发布时间和检查日期；无法访问内容则说明仅看到摘要，不伪称核实。
2. 用一句话记录目标用户、场景、动作和困难；首次只需一条可追溯线索，即可记录为 Signal。
3. 将真实动作提炼成最多 3 个自然英文搜索词，并标注搜索意图和地区；完成后可标 Keyword Candidate，不要求第二份证据。
4. 寻找第二份独立需求证据。Signal/Keyword Candidate 可写 unknown；不同作者和不同原始行为才算独立，转帖与转载不算。
5. 寻找明确商业化证据，包括实际用户付费、可靠的已付费服务、明确预算/购买/切换意愿或有用户使用迹象的收费替代。早期可记 unknown；价格、结账访问和广告并不等于成交。
6. GPT 自行检查可公开访问的 SERP：保存搜索地区、日期、结果类型、实际访问 URL 和已查看结果数量，判断是否存在「想执行工具动作却只有内容页」的供给缺口。不完整时不可宣称已核实前十。没有授权的 Semrush/Ahrefs/Similarweb 数据时，搜索量、KD、CPC、完整 SERP 盘面全部填 unknown，列为人工复核；有合法可靠来源才附日期填入。
7. 写清 7 天 MVP 的输入、处理、输出、API 依赖、成本、8–12 工时可行性、至少一个需求测试动作，以及版权、商标、合规风险。
8. 使用 normalized English demand query + search intent + user scenario 形成去重键，域名可为空；补充 first_seen/last_seen、来源、证据覆盖、适用维度评分和 `status_history`/`score_history`（带时间戳）。相同意图的新证据合并到原记录。

**Validated Opportunity 的硬门槛**：至少两条独立真实需求证据、一条可信商业化证据，以及经确认的 SERP 分析和 MVP 可行性判断。得分高不能绕过门槛；Signal 和 Keyword Candidate 不因缺证据而禁止入库。

## M11 用户授权数据的投递规范

仅从仓库 `inputs/gsc-ga4/` 读取用户明确提供的导出文件，不默认能访问 GSC 或 GA4 登录账户。推荐命名 `gsc_queries_pages_YYYY-MM-DD.csv` 与 `ga4_landing_pages_YYYY-MM-DD.csv`；GSC 至少包含 date、query、page、clicks、impressions、ctr、position（若导出是区间聚合数据，另附起止日期说明）；GA4 至少包含 date、landing_page、sessions、engagement_rate、average_engagement_time，及分析范围。两份数据必须标明属性/站点、时区、时间区间及维度定义。按规范化落地页关联，不能把不同粒度数据直接当成逐查询的会话时长。缺一份、无授权、格式不符或数据无法访问时：**跳过 M11 并记 blocked**，不能声称已完成检查。仓库是公开的，严禁上传含个人身份信息、密钥、用户级事件记录的原始数据。

## 人工补数据及数据分工

任务负责获取公开可访问的产品、帖子、评论和 SERP，提炼用户动作、关键词、竞品类型及供给缺口。用户用 Semrush/Ahrefs 等核实无法获取的 volume、KD、CPC；不可获取的值必须显示 unknown 并进入「人工待核」部分。

小红书、抖音、闲鱼、招聘 JD，以及需要登录或有反爬限制的 YouTube 评论，不绕过限制自动抓取；只接收用户授权提供的截图、文本、合法导出或链接，并标记人工提供、尚需复核。公开可合法访问的 YouTube 评论可分析。中文平台受众数据不能自动转化为英语市场证据。

## 产出数量与注意力限制

每天最多展示 **3 条达到推荐线**的新发现或显著升级候选；低于推荐线只入候选池/Watchlist，不凑数。按证据可靠度、得分率及覆盖维度排序，超出配额的候选存池待核。周日只推荐 1 个值得深挖的项目。允许 0 条。单条 Signal 只归档不推荐。报告分别统计 Signal、Keyword Candidate 与 Validated Opportunity，不把三者都称为已验证成功。
## 状态与评分（分阶段、缺失数据不扣零分）

- `Signal`：一条可追溯原始线索即可入库；只记录原始信号与各维度可观察信息，**不打总分、不进入每日推荐**。
- `Keyword Candidate`：用户动作、自然英文关键词和意图清晰；第二份独立证据、付费信息可为 unknown，不因此拒绝。
- `Validated Opportunity`：必须同时具备 ≥2 条独立需求证据、≥1 条可信商业化证据、可核验的 SERP 和 MVP 可行性检查；高分不可替代这些门槛。
- `Watchlist`：数据待核、缺关键证据或趋势尚不明朗；**数据缺失不构成 Rejected 理由**。
- `Rejected`：证明确为重复无增量、明显不匹配目标、版权/合规否决、开发成本显著超限等；记录确切理由。

| 维度 | 满分 | 有依据才评分 |
|---|---:|---|
| 真实痛点/独立来源 | 25 | 可复核用户行为、频率、证据 |
| 商业化/付费证据 | 20 | 报价并有采用迹象、实际支付、预算或切换意愿 |
| SEO 获客机会 | 20 | 公开 SERP 搜索意图、工具供给缺口、真实竞争格局；不能编造 KD/volume |
| 7 天 MVP 可实现性 | 20 | 功能范围、API 与维护成本有合理依据 |
| 持续性与差异化 | 15 | 长期场景、细分差异、重复使用 |

**计分算法**（仅 Candidate 和 Validated 适用）：
1. 对有足够可信依据的维度记录 `earned/max`；无依据填 `unknown`，整个维度**不进分子也不进分母**，不可按 0 计算。
2. `covered_weight = Σ(已评分维度满分)`；`normalized_score = Σ(已获分) / covered_weight × 100`，注明 **「基于 N/5 维度、覆盖权重 W/100」**。若覆盖权重为 0 则得分 unknown。
3. **每日推荐入围**：`normalized_score >= 60`、至少 **3/5 个维度可评分**且覆盖权重至少 **55/100**，存在可核验原始证据链接及实际可执行的下一步；否则仅归档或 Watchlist。优先排序 Validated，其次 Candidate，再比较覆盖权重与证据质量。达到推荐线**不意味着**升级为 Validated。
4. `normalized_score < 60` 不进入每日推荐；如低分主要由无法取得的关键数据引起，保留 Watchlist/人工待核而非 Rejected。实查可得信息证明需求很弱时才可给该维度低分，**“缺失”与“否定性证据”必须区别**。
5. 版权侵权、禁止的采集方式、不可负担 API 等单独检查，不能因为评分高跳过。

**例子**：某 Candidate 有需求 18/25、MVP 16/20、持续性 11/15，商业和 SEO 均 unknown：45/60=75 分（覆盖 3/5、60/100），达到初步推荐线，但仍只是待商业和 SEO 复核的 Candidate；不得称已验证机会。若仅 MVP 一维 20/20，尽管标准化得分 100，也因只覆盖 1/5 不得推荐。

## 输出格式（每条）

```markdown
### 候选名称 — 状态（Signal / Keyword Candidate / Validated Opportunity）
- 日期：首次发现 / 本次检查
- 方法：Mxx；去重键：标准化英文需求词+搜索意图+用户场景（域名可为空）
- 用户：谁 / 场景 / 高频操作与困境
- 用户动作：英文一句话
- 关键词：英文词1 / 词2 / 词3（各自意图）
- 证据1：原始直链 + 日期 + 简短原话或行为
- 证据2：独立原始直链 + 日期 + 简短原话或行为（没有则未验证）
- 付费信号：具体替代方案、定价或购买意愿 + 来源（没有则未验证）
- SERP：搜索引擎/地区/日期、真实访问的结果 URL、已核查数量、可能的供给缺口（未查到填 unknown）
- 数据：volume、KD、CPC、trend及来源/日期；无法查写 unknown 并放入人工待核
- 评分：Signal 填“未评分”；其他状态逐维填写 earned/max 或 unknown，并给出 normalized_score、覆盖 N/5 与 W/100；是否达到 ≥60 推荐线
- 7天 MVP：输入 → 处理 → 输出；试验方式；主要开发/运维成本
- 风险：版权/商标/API/数据访问/竞争
- 下一步：一个具体待验证动作
```

运行汇总：固定轮换组合、检查来源、原始信号/去重/各状态/升级/淘汰数量、最多 3 个达到推荐线的候选（可以为 0）、缺失指标人工待核清单，以及访问失败说明。周日报告只基于候选池本周的状态/评分变化，并明确声明不是逐日扫描报告的全文回顾。**无合格机会时如实写 0，不用拼凑日报。**

## 未来执行时建议的仓库存储
- `reports/YYYY-MM-DD.md`：逐日运行记录。
- `data/opportunities.jsonl`：唯一常规去重/周报来源，包含按词+意图+场景生成的稳定 ID、first_seen/last_seen、status、status_history、score_history（含时间）、evidence_url(s)、competitor_domains、keywords、各维度 earned/max/unknown、覆盖权重；按 ID 合并、保留旧记录与变化史。
- `data/checkpoints.json`：每个监测源的最近成功扫描时间、失败原因和增量标记。

**同日重跑写入规范**：先读取现有 `reports/YYYY-MM-DD.md` 与候选池，把当日新增记录按 ID 合并（保留先前证据与检查结果、更新最后检查时间）；最终**整份重写该日期的 report**，不直接盲目覆盖也不重复追加。同一证据 URL 去重；`opportunities.jsonl` 按稳定 ID 做 upsert（存在则合并/更新该行，不存在才追加新行），不得原样无限追加重复对象。先获取最新 SHA，写入前冲突要重新读取并合并，禁止强制覆盖。写入失败报告原因。原始剪存目录始终只读。
